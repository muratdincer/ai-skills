# Write a Pull Request Description

## Purpose
Give reviewers everything they need to review quickly and safely: intent, scope, design choices, test evidence and risk. A good description shortens review cycles and becomes the searchable record of why the code looks the way it does.

## When to use
- Opening a pull/merge request from a branch with one or more commits.
- A PR changed significantly after review and the description is stale.
- A large or risky change needs a guided review order.

## When not to use
- A single commit message. Use `commit-message`.
- The design is still open and needs discussion before coding. Use `technical-design-doc`.
- Reviewing someone else's PR. Use `code-review`.

## Inputs
Required:
- The diff, the commit list, or a clear description of the change.

Optional, improves quality:
- Linked work item and its acceptance criteria.
- Test results, screenshots or recordings for UI changes.
- Deployment notes: migrations, feature flags, configuration, dependent services.
- The team's PR template.

If no change information is given, ask for it. If test evidence is missing, do not claim tests were run; add `[TBD: test evidence]`.

## Process
1. Summarize the change in one or two sentences from the reviewer's point of view: what behavior is different after merge.
2. State why: link the work item or describe the problem. If the reason is not given, mark `[TBD]`.
3. List the changes grouped by concern (domain logic, API, data, UI, config, tests), not by file.
4. Highlight design decisions and alternatives rejected, so reviewers do not relitigate them unknowingly.
5. Describe how it was tested: automated tests added or changed, manual steps with environment, what was not tested and why.
6. Identify risks: data migration, backward compatibility, performance, security surface, concurrency. For each, state the mitigation.
7. Write deployment and rollback notes: order of steps, flags, migrations (reversible or not), required config.
8. Propose a review order and point out the files that need the closest attention; mark generated or mechanical changes as skim-only.
9. If the PR exceeds roughly 400 changed lines of hand-written code or mixes refactoring with behavior change, recommend splitting and show how.
10. Fill the template; remove sections that truly do not apply rather than writing "N/A" everywhere.
11. Suggest next steps from `related` when the goal continues: `code-review` for a self-review before requesting reviewers, `rollback-plan` when the Risks section shows an irreversible change, `release-notes` when the change is user-facing.

## Output format
```markdown
## Summary
<1-2 sentences: behavior after merge>

## Why
<problem / work item link or [TBD]>

## Changes
- <concern>: <change>

## Design Notes
- Decision: <...> — Alternative considered: <...> — Reason: <...>

## How Tested
- Automated: <tests added/changed>
- Manual: <steps, environment>
- Not tested: <gap and reason>

## Risks and Mitigations
| Risk | Impact | Mitigation |
|---|---|---|

## Deployment / Rollback
- <migrations, flags, config, order of steps>

## Review Guide
1. Start with <file/area> — <why>
- Skim only: <generated / mechanical changes>

## Screenshots (UI changes only)
```

## Quality checklist
- [ ] The summary describes behavior, not a list of files.
- [ ] The "why" is present or explicitly `[TBD]`.
- [ ] Test evidence is factual; nothing claims tests ran without evidence.
- [ ] Irreversible steps (migrations, data changes) are called out with rollback implications.
- [ ] Reviewers know where to start and what to skim.
- [ ] Oversized or mixed PRs get a concrete split proposal.
- [ ] All checks pass; if any fails, revise the output and re-run this checklist before answering.

## Common pitfalls
- Restating commit subjects as the description. Reviewers need intent and risk, not a changelog of the branch.
- Omitting what was not tested. Silence reads as "fully tested" and shifts risk to reviewers unknowingly.
- Forgetting deployment coupling (e.g., consumer must deploy before producer). State ordering explicitly.

## Example
Input: Commits "add InvoicePdfJob", "enqueue job on invoice finalize", "remove sync PDF call", "add job retry tests".

Excerpt of output:
- Summary: Invoice PDFs are now generated by a background job after finalization; the finalize endpoint no longer blocks on PDF rendering.
- Risk: Users may open an invoice before its PDF exists — Mitigation: UI shows "generating" state; `[TBD: confirm UI change is in scope]`.
- Deployment: Worker must be deployed and consuming the queue before the API change; otherwise PDFs are never produced.
